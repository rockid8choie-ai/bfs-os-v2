BFS OS API 기능 명세서

빌딩 시설 운영 — 접수, 담당자 배정, 민원 전환을 위한 REST API

문서 버전 1.0 · 2026-09-02 · Base URL https://bfs-os-v2.vercel.app · 저장소 https://github.com/rockid8choie-ai/bfs-os-v2

1. 개요

프론트엔드(Next.js)와 같은 애플리케이션에 구현된 REST API입니다. 요청은 JSON으로 주고받으며, 업무 데이터는 Postgres(Neon)에 저장됩니다.

항목내용
프로토콜HTTPS, JSON
인증로그인 성공 시 httpOnly 쿠키 bfs_session (JWT, 유효기간 7일)
권한같은 건물만 조회. 소장(manager)은 전체, 시설팀(tech)은 자기 작업만
성공 형식{ "data": ... }
실패 형식{ "error": { "code": "...", "message": "한글 설명" } }

2. 상태 코드 · 에러 코드

HTTPcode의미
200 / 201—성공. 생성은 201
400VALIDATION요청 본문 검증 실패
401UNAUTHORIZED미로그인, 세션 만료, 잘못된 비밀번호
403FORBIDDEN역할 권한 없음 (예: 시설팀의 민원 전환)
404NOT_FOUND작업/민원 없음
500INTERNAL서버 오류
503UNAVAILABLEDB 연결 실패 (health)

  "error": {
    "code": "UNAUTHORIZED",

  }
}

5. 상세 명세

GET /api/health 공개

데이터베이스 연결을 확인합니다. 인증이 필요 없습니다.

성공 200

{
  "data": {
    "ok": true,
    "service": "bfs-os",
    "time": "2026-09-02T05:24:34.131Z"
  }
}

실패 503 DB 미연결 — code UNAVAILABLE

POST /api/auth/login 공개

이메일·비밀번호를 확인한 뒤 JWT를 발급하고 bfs_session 쿠키를 심습니다. 응답 body에도 token을 포함합니다.

Request

{
  "email": "park@bfs.local",
  "password": "demo1234"
}
필드필수규칙
emailO이메일 형식. 소문자로 정규화
passwordO8자 이상

성공 200

{
  "data": {
    "token": "<jwt>",
    "user": {
      "id": "cmtj...",
      "name": "박정호",
      "role": "manager",
      "title": "관리소장",
      "email": "park@bfs.local",
      "phone": "010-2841-0033",
      "years": 12,
      "specialty": ["소방·안전"],
      "buildingId": "cmtj...",
      "buildingName": "역삼타워"
    }
  }
}

실패 400 이메일/비밀번호 형식 · 401 이메일 또는 비밀번호가 올바르지 않습니다.

GET /api/auth/me 인증

쿠키의 JWT로 현재 사용자를 반환합니다.

성공 200 { "data": { "user": { ... } } } (login의 user와 동일 형태)

실패 401 로그인이 필요합니다. / 세션이 만료되었습니다.

POST /api/auth/logout

세션 쿠키를 삭제합니다. 본문 없음.

성공 200

{ "data": { "ok": true } }

GET /api/members 인증

같은 건물 구성원과 현재 부하를 반환합니다. 배정 시트에서 사용합니다.

성공 200

{
  "data": {
    "members": [
      {
        "id": "...",
        "name": "김태식",
        "role": "tech",
        "title": "시설팀 · 기계",
        "specialty": ["배관·급수", "공조·환기"],
        "phone": "010-5521-7788",
        "years": 8,
        "load": 2,
        "doneToday": 0
      }
    ]
  }
}

load = 상태가 배정됨·진행중인 건수. doneToday = 완료 건수.

POST /api/work-orders 인증

작업을 생성합니다. autoAssign이 false가 아니면 담당자를 붙입니다. 소장은 추천 규칙, 시설팀은 본인에게 배정합니다.

Request

{
  "title": "3층 화장실 온수가 안 나와요",
  "location": "3F 화장실",
  "priority": "높음",
  "specialty": "배관·급수",
  "source": "AI 접수",
  "due": "오늘",
  "autoAssign": true
}
필드필수규칙
titleO2~120자
priorityO긴급 | 높음 | 보통
specialtyO전문분야 enum
sourceX기본값 "AI 접수"
location, dueX없으면 "위치 미지정", "오늘"
assigneeIdX지정 시 해당 담당자
autoAssignX기본 true. false면 대기 상태로만 생성
vocIdX민원과 연결할 때

성공 201 { "data": { "order": { ... } } }

실패 400 제목을 2자 이상 입력해 주세요. 등

PATCH /api/work-orders/:id 인증

action으로 배정과 상태 진행을 나눕니다.

배정 Request

{ "action": "assign", "assigneeId": "<userId>" }

소장: 건물 내 아무 담당자. 시설팀: 자기 id만. 완료된 작업은 담당자만 바꾸고 상태는 유지합니다. 배정 이력(AssignmentEvent)을 남깁니다.

진행 Request

{ "action": "advance" }

배정됨 → 진행중 → 완료. 완료 시 연결된 민원도 트랜잭션으로 완료. 대기(미배정) 작업은 400.

성공 200 { "data": { "order": { ... } } }

실패 400 담당자를 먼저 배정해야 시작할 수 있습니다. · 403 배정받은 작업만 처리할 수 있습니다. · 404 작업을 찾을 수 없습니다.

GET /api/vocs 인증

같은 건물 민원 목록. 연결된 작업은 workOrderId.

성공 200

{
  "data": {
    "vocs": [
      {
        "id": "...",
        "title": "천장에서 물이 떨어져요",
        "tenant": "302호 · 그린테크",
        "createdAt": "오늘 08:40",
        "status": "접수",
        "aiTag": "배관·누수",
        "specialty": "배관·급수",
        "workOrderId": "..."
      }
    ]
  }
}

POST /api/vocs/:id/convert 인증 · 소장

민원을 작업지시로 전환합니다. 이미 연결된 작업이 있으면 새로 만들지 않고 기존 id를 반환합니다. 시설팀은 403.

성공 200 (기존 작업) / 201 (신규 생성)

{
  "data": {
    "order": { "id": "...", "title": "302호 천장에서 물이 떨어져요", "status": "대기", ... },
    "voc": { "id": "...", "status": "처리중", "workOrderId": "..." },
    "created": true
  }
}

실패 403 민원 전환은 관리소장만 할 수 있습니다. · 404 민원을 찾을 수 없습니다.
